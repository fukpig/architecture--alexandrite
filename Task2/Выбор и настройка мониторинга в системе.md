## Выбор подхода к мониторингу

| Подсистема                              | Подход к мониторингу                                         | Почему                                                                                                 |
|------------------------------------------|--------------------------------------------------------------|--------------------------------------------------------------------------------------------------------|
| RabbitMQ                                | USE (Utilization, Saturation, Errors)                        | RabbitMQ — это инфраструктурный компонент. Важно знать, насколько он загружен и есть ли потери.        |
| Интернет-магазин, CRM, MES (API)        | RED (Rate, Errors, Duration)                                 | Эти сервисы ориентированы на взаимодействие с пользователями. RED хорошо покрывает производительность и надёжность. |
| Базы данных                             | USE + метрики из «Четырёх золотых сигналов»                  | Высокая нагрузка и риск узких мест требует оценки ресурсов и ошибок.                                   |
| Общее состояние системы                 | Четыре золотых сигнала (Latency, Traffic, Errors, Saturation) | Для мониторинга end-to-end процессов (например, время от SUBMITTED до MANUFACTURING_STARTED)           |


## Выбранные метрики и обоснование
RabbitMQ (USE)
Number of dead-letter-exchange letters in RabbitMQ
— Зачем: выявляет потерянные/отклонённые заказы.
— Ярлыки: queue, message_type.

Number of messages in flight in RabbitMQ
— Зачем: отражает текущую нагрузку и задержки в обработке.
— Ярлыки: queue, source_service, target_service.

API (RED) — интернет-магазин, CRM, MES
Number of requests (RPS) for shop/CRM/MES API
— Зачем: общая нагрузка на систему.
— Ярлыки: method, endpoint, status_code.

Number of requests (RPS) per user for shop/CRM/MES API
— Зачем: выявление «шумных» клиентов, возможных атак или ботов.
— Ярлыки: user_id, endpoint.

Response time (latency) for shop/CRM/MES API
— Зачем: важнейший показатель UX. Показывает, где узкое место.
— Ярлыки: endpoint, status_code, method.

Number of HTTP 500 для shop/CRM/MES API
— Зачем: показывает сбои в логике или инфраструктуре.
— Ярлыки: endpoint, method.

Number of HTTP 200 для shop/CRM/MES API
— Зачем: для отслеживания общей успешности.
— Ярлыки: endpoint.

Number of simultaneous sessions для shop/CRM/MES API
— Зачем: оценка пиковых состояний и предельной нагрузки.
— Ярлыки: service_name, region.

Kb transferred (received) / provided (sent)
— Зачем: мониторинг объёма переданных данных, особенно актуален для 3D-моделей.
— Ярлыки: endpoint, direction, user_id.

Инфраструктура и базы данных (USE + общие сигналы)
CPU % и Memory Utilisation для shop/CRM/MES API
— Зачем: нагрузка на приложение, пиковые значения могут привести к сбоям.
— Ярлыки: service_name, instance_id.

Memory Utilisation для shop/MES DB instance
— Зачем: оценка ресурсов для кэширования, рост может привести к swap.
— Ярлыки: db_instance.

Number of connections for shop/MES DB instance
— Зачем: оценка нагрузки на соединения, возможные утечки.
— Ярлыки: application, user, host.

Size of shop/MES DB instance
— Зачем: понимание роста данных, планирование масштабирования.
— Ярлыки: db, table (если есть).

Size of S3 storage
— Зачем: объём хранимых моделей, контроль за потреблением.
— Ярлыки: bucket, content_type.


## План действий

Выбор и развертывание системы мониторинга
Задача: Выбрать стек мониторинга (предпочтительно: Prometheus + Grafana + Alertmanager).

Детали:

Создать отдельный EC2-инстанс под Prometheus.

Настроить time-series хранилище (внутреннее TSDB или VictoriaMetrics для нагрузки >10k метрик).

Настроить retention данных (например, 30 дней).

Настроить Grafana и подключить источники (Prometheus, Yandex Cloud Monitoring).

2. Интеграция с RabbitMQ
Задача: Настроить экспорт метрик RabbitMQ через Prometheus RabbitMQ Exporter.

Метрики:

messages_ready, messages_unacknowledged, messages_published_total, messages_dropped_total

dead-letter, in-flight, backlog

Теги (ярлыки): queue, exchange, vhost, source_service, target_service.

3. Инструментирование API сервисов
Задача: Добавить Prometheus-интеграцию во все API: онлайн-магазин, CRM, MES.

Метрики:

RPS, latency, status codes (200/500), нагрузка на пользователя (per user).

Технология: Использовать Spring Boot Actuator + Micrometer (для Java), Prometheus.NET (для C#).

Лейблы: endpoint, method, status_code, user_id.

4. Интеграция с базами данных
Задача: Настроить экспорт системных метрик из PostgreSQL (и MS SQL, если MES на ней).

Метрики:

Кол-во соединений, использование памяти, размер таблиц, iops.

Технология: postgres_exporter, mssql_exporter.

5. Мониторинг системных ресурсов
Задача: Развернуть node-exporter на всех EC2-инстансах.

Метрики: CPU, Memory, Disk, Network IO.

Дополнительно: Установить blackbox_exporter для внешнего мониторинга доступности API.

6. Создание бизнес-метрик по жизненному циклу заказа
Задача: Внедрить кастомные метрики времени прохождения стадий заказа (SUBMITTED → PRICE_CALCULATED и т.д.).

Метод:

Отправка кастомных Prometheus-метрик из CRM и MES при изменении статусов заказов.

Возможная альтернатива: писать в Kafka + отдельный job для метрик.

7. Настройка алертинга
Задача: Развернуть и настроить Alertmanager.

## Сценарии алертов:

Рост HTTP 500.

Рост времени ответа MES > 5s.

Очередь RabbitMQ > N сообщений.

Заказ находится в SUBMITTED более 1 часа.

Дашборд MES загружается более 10 секунд.
