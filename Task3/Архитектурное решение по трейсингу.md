## Мотивация

Заказ проходит через три системы (онлайн-магазин → MES → CRM) и несколько асинхронных очередей. Ошибки часто происходят «где-то посередине», и найти их сложно.
Сквозная видимость прохождения заказа;

Возможность быстро понять, на каком шаге заказ завис;

Отладка цепочек: от API до RabbitMQ и обратных ответов.

Сейчас команда узнаёт о проблемах от клиента, и даже потом требуется часы ручной проверки логов в разных системах.Точные ответы: «заказ завис в MES при расчёте стоимости», «сообщение RabbitMQ не дошло»; ускорение раследования инцидентов.
полную видимость жизненного цикла каждого заказа;

## Обязательные для покрытия:

Интернет-магазин (Spring Boot)
— создание заказа, загрузка модели, вызов MES на расчёт.

MES (C#)
— расчёт стоимости, взятие заказа в работу, завершение.

CRM (Java Spring Boot)
— подтверждение заказа, закрытие.

RabbitMQ
— входящие/исходящие сообщения. Потенциальный источник потерь.

Очереди и обработчики фоновых задач
— генерация PDF, отправка уведомлений, приём сообщений API-партнёров.



## Предлагаемое решение

| Компонент                      | Решение                                                                 |
|--------------------------------|-------------------------------------------------------------------------|
| Трейсинг                       | OpenTelemetry как стандарт                                              |
| Аггрегация/визуализация        | Grafana Tempo или Jaeger                                                |
| Интеграция с Spring Boot       | opentelemetry-java-instrumentation или micrometer-tracing               |
| Интеграция с C# (MES)          | OpenTelemetry .NET SDK                                                  |
| RabbitMQ                       | Обёртка для publisher/subscriber, передача trace_id                     |
| Визуализация                   | Tempo + Grafana Traces View или Jaeger UI                               |

## Какие моменты подсветит трейсинг
### Технические:
Время прохождения заказа от SUBMITTED до SHIPPED

Количество заказов, застрявших более N минут на стадии

Доля заказов с превышением SLA расчёта стоимости

Общее число «сломанных» трассировок (неполных)

### Бизнес:
Снижение количества обращений в поддержку по потерянным заказам

Скорость выявления багов (MTTR)

Сохранение контрактов B2B за счёт прозрачности


## Безопастность 
Аутентификация через SSO или IAM
— только сотрудники с ролью “Поддержка”, “DevOps” или “Dev” имеют доступ к просмотру трассировок.

Маскирование персональных данных в trace-тегах
— вместо user_email → user_id.

TLS между компонентами трейсинга (Collector ↔ Tempo ↔ Grafana)
— защищённая передача метаданных.

Логи аудита доступа к системе трейсинга
